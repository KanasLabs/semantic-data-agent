Runtime、Hybrid 与 Codex SDK 自改进架构说明

这份文档说明三个问题：什么是 Agent Runtime；在智能问数项目里如何划分 Runtime；以及 Codex SDK 如何作为自改进 Runtime，接入 Hybrid 业务 Runtime 形成受控自改进闭环。

核心判断：Hybrid 是在线问数业务 Runtime 的核心架构；Codex SDK 更适合作为自改进闭环中的工程型 Runtime，用来消费 trace、反馈和 eval，产出可审查的候选改动。
概念层

Runtime

面向某一类作业的后端执行能力，不是某一次任务，也不等同于 agent loop。

业务层

Hybrid Business Runtime

负责在线问数：用户交互、Wren 语义检索、SQL 生成、执行、安全控制和 trace。

改进层

Codex Improvement Runtime

负责后台工程改进：定位失败、修改代码/规则/测试、跑 eval、输出候选 diff。

2. Runtime 的工作定义

在这里，Runtime 可以理解为实现某一类作业的后端能力。它不是单纯的“循环”，而是能够承载模型调用、工具调用、状态管理、上下文管理和执行约束的一组后端能力。

Agent = 决策者
Agent loop = 决策 - 行动 - 观察 - 再决策的控制循环
Agent Runtime = 承载某类 agent 作业执行的 backend
Task / Goal = 某次要完成的具体目标

Runtime 应该按什么区分

  • 它承载哪一类 bounded task
  • 它有哪些工具和权限
  • 它管理什么状态和上下文
  • 它输出什么结果
  • 它如何被验证和审查

Runtime 不应该被误解为

  • 不是某一次任务本身
  • 不是单纯的 prompt 调用
  • 不等于 agent loop 这个控制结构
  • 不等于某个具体模型
  • 不等于 provider 或 channel
更稳的表述：Runtime 是 Business Loop 可调用的 agent execution backend。Business Loop 负责任务定义、上下文准备、边界约束和验收标准；Runtime 负责在这些约束下执行。

3. 本项目里的两个 Runtime

在智能问数项目里，Runtime 可以按照作业类型拆成两类：一个负责在线问数，一个负责后台自改进。它们是上下游关系，不是同一个执行层。

Hybrid Business Runtime 在线问数作业：回答当前用户问题
  • 输入：用户问题、权限、Wren 语义层、上下文
  • 执行：澄清、检索、SQL 生成、dry-run、execute、图表解释
  • 输出：答案、图表、SQL、trace、用户反馈入口
  • 验收：正确性、安全性、权限合规、延迟和可解释性
→
Codex Improvement Runtime 自改进作业：改进下一版问数系统
  • 输入：trace、失败案例、专家标注、eval、代码库、Wren 配置
  • 执行：定位原因、修改 prompt/rules/mapping/tests、跑评测
  • 输出：候选 diff、测试结果、修复说明、风险说明
  • 验收：eval 提升、回归通过、专家和工程师 review
关键关系：Hybrid Runtime 产生 trace 和反馈；Codex Runtime 消费这些材料，产出候选改动；候选改动经过 review 后反哺下一版 Hybrid Runtime。

4. Hybrid 是业务 Runtime 的核心架构

Hybrid 不是自改进 Runtime，而是在线问数业务 Runtime 的核心执行架构。它解决的是“这一次用户的问题怎么稳定、合规、可解释地回答”。

用户问题
 -> 外层 General Agent 判断意图、澄清问题、选择工具
 -> 调用 ask_data_question
 -> Wren context retrieval
 -> SQL generation
 -> Wren semantic engine dry-run / execute
 -> SQL guardrail / permission check
 -> 结果格式化 / 图表 / 解释
 -> trace logging / 用户反馈

外层 Agent

负责交互、澄清、任务调度、多轮对话和结果解释。

受控问数工具

ask_data_question 内部走固定 pipeline，不能让 Agent 绕过安全和权限层。

Wren 语义地基

提供 context layer 和 semantic engine，支撑业务口径、SQL 转译、dry-run 和执行。

5. Codex SDK 更适合作为自改进 Runtime

Codex SDK 的价值不在于替代在线问数链路，而在于提供一个工程型 agent runtime：它能读取项目、理解代码、修改文件、运行测试、分析失败并输出可审查的候选改动。

这里的“候选改动”不只指代码改动，也包括 Wren Context Layer、business rules、confirmed examples、eval cases、prompt 模板和 guardrail 配置等工程资产。

Codex Runtime 适合做什么

  • 读取代码库、prompt 模板、Wren 配置和 eval
  • 分析失败 trace 对应的错误环节
  • 修改 mapping、business rules、prompt、guardrail 或测试
  • 运行定向 eval 和回归测试
  • 生成候选 diff、修复说明和风险说明

Codex Runtime 不适合直接做什么

  • 直接承接线上用户的实时问数请求
  • 绕过 Wren、权限系统或 SQL guardrail 查询数据库
  • 无审查地自动修改生产语义层
  • 无 eval gate 地自动发布系统变更
设计边界：Codex SDK 应该在后台自改进链路中执行 bounded engineering task，而不是进入用户实时问数主链路直接响应业务查询。

6. 自改进不只针对代码

在智能问数项目里，自改进最重要的对象往往不是业务代码，而是系统对业务语义的结构化理解。Wren Context Layer 正是这类语义资产的核心载体。

Wren Context Layer 包含什么

  • models / views / relationships
  • metrics / metric definitions
  • business rules
  • 字段描述、单位、枚举含义
  • 默认过滤条件
  • confirmed NL-SQL examples

Codex 可以产出哪些候选改动

  • 新增 confirmed NL-SQL example
  • 新增或修正 eval case
  • 补充字段描述和业务术语解释
  • 建议新增 business rule
  • 修正 metric definition
  • 必要时修改 prompt、mapping 或 guardrail
更推荐的优先级：先改进语义资产、样例库和评测集，再考虑修改核心代码。这样风险更低，也更贴近 Tax AI 式闭环。

GMV 口径错误的例子

假设用户问“上个月华南区 GMV 为什么下降”，系统生成的 SQL 错误地把 GMV 算成 order_count，而不是 payment_amount。这个问题未必需要先改代码，更可能是 Wren 语义层缺少明确的 GMV 口径。

trace 记录：
- 原始问题：上个月华南区 GMV 为什么下降
- 检索到的 Wren context
- 生成的 SQL
- dry-run / execute 结果
- 用户点踩
- 专家标注：GMV = sum(payment_amount)，只统计 paid orders

Codex Runtime 可生成的候选改动：
1. 更新 Wren metric definition
   GMV = sum(payment_amount), filter status = 'paid'

2. 新增 business rule
   所有 GMV 查询默认排除 canceled / refunded orders

3. 新增 confirmed NL-SQL example
   “上个月华南区 GMV” -> 正确 SQL

4. 新增 eval case
   输入同类问题，期望 SQL 包含 payment_amount 和 status = 'paid'

5. 如有必要，修改 prompt
   强制优先使用 Wren metric definitions
改进对象 是否适合 Codex 生成候选改动 风险等级 控制方式
confirmed NL-SQL examples 很适合 低 可半自动，但要保留来源和版本。
eval cases 很适合 低 可半自动加入候选评测集。
字段描述 / 业务术语解释 适合 中 需要业务专家确认。
business rules / metric definitions 适合 中 需要业务专家确认，并通过 eval。
prompt 模板 适合 中 需要 eval gate 和回归测试。
Wren relationships / model 结构 可以，但要谨慎 高 需要工程师 review、专家确认和回归测试。
SQL guardrail / 权限规则 / 核心代码 可以，但风险最高 高 必须工程 review，不应自动上线。

7. Codex SDK 如何接入受控自改进闭环

受控自改进闭环不是让系统无监督地自己改自己，而是把失败案例变成可验证、可审查的工程任务，再交给 Codex Runtime 执行。

1. Trace

Hybrid Runtime 记录问题、context、prompt、SQL、dry-run、执行结果和用户反馈。

2. Failure Mining

聚合高频失败，判断是语义层、SQL 生成、权限、映射还是图表解释问题。

3. Bounded Task

Business Loop 准备任务说明、失败样例、专家标注、eval 和修改边界。

4. Codex Runtime

Codex SDK 执行工程修复，修改语义层、规则、样例、prompt、代码或测试并运行评测。

5. Review Gate

专家和工程师审查候选 diff，评测通过后发布到下一版 Hybrid Runtime。

失败 trace / 用户反馈 / 专家标注 / eval
 -> Business Loop 生成 bounded task
 -> 调用 Codex SDK 作为 Improvement Runtime
 -> Codex 读取 repo、Wren 配置、prompt、eval、trace
 -> Codex 定位失败原因
 -> Codex 修改候选语义层、样例、规则、prompt、代码或测试
 -> Codex 运行定向 eval 和 regression
 -> 输出候选 diff + 测试结果 + 修复说明
 -> 专家 / 工程师 review
 -> 合并后反哺下一版 Hybrid Business Runtime

8. 一个更具体的接入实现

工程上可以把 Codex SDK 封装成自改进服务中的一个 Runtime Adapter。上层 Business Loop 不直接关心 Codex 内部如何 loop，只关心任务边界、输入材料、输出结果和验证状态。

模块 职责 关键产物
Trace Store 保存每次问数的结构化链路。 request trace、SQL、context、错误、用户反馈。
Failure Miner 聚合失败案例，识别高频问题和根因候选。 failure cluster、优先级、问题类型。
Eval Manager 维护定向 eval 和回归测试。 eval set、baseline、pass/fail report。
Task Composer 把失败聚类、专家标注和验收标准组织成 bounded task。 任务说明、上下文包、允许修改范围。
Codex Runtime Adapter 调用 Codex SDK 执行工程修复任务。 candidate diff、测试结果、执行 trace。
Review Gate 控制专家和工程师审查、合并和发布。 review 结论、合并记录、发布版本。
这里的 Codex SDK 是 Runtime Adapter 背后的执行能力；Business Loop 负责把“业务失败”翻译成“有边界的工程任务”。

9. 边界与风险控制

自改进闭环必须受控。Codex Runtime 可以生成候选改动，但不应该直接无审查地修改生产系统。

风险等级 可执行动作 控制方式
低风险 新增 confirmed NL-SQL example、生成失败报告、补充 eval case。 可半自动执行，但需要记录来源和版本。
中风险 建议新增 business rule、修改字段描述、补充 metric definition。 需要领域专家确认。
高风险 修改 Wren model / relationship、权限规则、SQL guardrail、核心 prompt。 需要工程师 review、eval gate 和回归测试。
最重要的限制：Codex Runtime 产出的是候选改动，不是自动发布结果。发布权应该留在 review gate 和 CI / eval gate 后面。

10. 结论

Hybrid 负责跑业务

Hybrid Business Runtime 解决“这一次怎么可靠地回答用户”：交互、语义检索、SQL 生成、执行、安全控制、结果解释和 trace。

Codex 负责改进系统

Codex Improvement Runtime 解决“下一版系统怎么变得更好”：消费 trace 和 eval，执行有边界的工程修复，产出可审查的语义层、规则、样例、prompt、测试或代码候选改动。

一句话：本项目中可以按作业类型区分 Runtime。Hybrid 是在线问数业务 Runtime；Codex SDK 是受控自改进闭环中的工程型 Runtime。Codex 的自改进不只改代码，更重要的是改进 Wren Context Layer、业务规则、confirmed examples 和 eval set 等业务语义资产。

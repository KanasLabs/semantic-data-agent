> 自改进不是一个会无限修改自己的 Agent，而是一条“从失败证据生成受控候选”的后台工程流程。

## 一、它不是五个 Subagent

SI0、SI1、SI2、SI3 更准确地说是阶段或能力等级，不是四个独立 Agent。

```text
Self-Improvement Controller
  ├─ Evidence Store
  ├─ Triage / EvalTarget
  ├─ Context Candidate Executor
  ├─ Future Code Candidate Executor
  └─ Validation / Review Gates
```

只有生成复杂候选或分析复杂问题时，才调用 Codex CLI。

## 二、最简流程

```text
生产错误 / 用户纠正
  ↓
保存证据
  ↓
确认“正确行为是什么”
  ↓
冻结验收标准
  ↓
确定修改目标
  ├─ Context Layer
  └─ Source Code
  ↓
Codex 生成候选
  ↓
外层确定性评测
  ↓
人工 Review
  ↓
单独发布
```

这里最重要的是先知道“正确答案是什么”，再允许 Codex修改。

## 三、SI0 做什么

SI0 只是收集和标准化证据：

- 问题
- 旧答案
- 旧 SQL
- Trace
- Eval 失败
- 用户纠正
- Context 版本
- 数据版本

SI0 不调用 Codex，也不修改任何内容。

当前已经实现。

## 四、SI1 做什么

SI1 将一个或多个 FailureCase 整理成 Finding，并冻结 EvalTarget。

例如：

- 业务规则：只有 completed 订单算已实现收入
- 预期数值：721.80
- 单位：CNY
- SQL 必须包含：status = 'completed'
- 答案禁止包含：$

聚类不是必需步骤。只有大量相似错误时才聚类；明确的业务纠正可以直接形成单例 Finding。

当前已经实现。

## 五、SI2 做什么

SI2 是一种 Candidate Job：

```text
target_type = WREN_CONTEXT
```

Codex 获得：

- 最小化 Evidence Pack；
- 冻结 EvalTarget；
- Wren candidate 副本；
- 允许修改的 Context 路径。

Codex只能生成 Context 候选，不能批准或发布。

当前已实现，并且真实调用 Codex 跑过。

## 六、外层评测做什么

外层评测不负责理解所有根因，只回答一个问题：

> 这个候选是否通过冻结验收标准？

结果先简化成：

- PASS
- FAIL
- BLOCKED

- PASS：进入人工 Review。
- FAIL：候选没有解决问题，进入人工或 Codex 辅助诊断。
- BLOCKED：数据库、网络或 EvalTarget 有问题，不能评价候选。

它不需要自动证明“根因一定在源码”。

## 七、SI3 做什么

SI3 是另一种 Candidate Job：

```text
target_type = SOURCE_CODE
```

Codex 在隔离 Git worktree 中修改源码，外层运行冻结测试和完整回归，最终只生成 PR candidate。

当前 development-only 控制器已经实现并完成一次真实 Codex CLI 最小案例。
正式 Docker/CI worker、签名 isolation receipt 和可发布源码结果仍未实现。

进入 SI3 前必须先有人工复核的不可变 `RoutingDecision`。正常流程不是让
Codex 直接决定修复层级，而是：

```text
Codex 收集和解释诊断证据
  → RoutingProposal
  → 外层控制器机械校验证据组合
      ├─ READY_FOR_REVIEW → 人工确认 → RoutingDecision
      └─ DIAGNOSIS_REQUIRED → 补充证据，不能启动 Job
  → SI2 / SI3
```

`RoutingProposal` 会保留建议目标、typed evidence、Codex/调用方给出的理由，
以及确定性控制器的完整错误列表。即使证据不足也会保存，但不能被确认。
人工确认后生成独立 `RoutingDecision`，并通过 SHA-256 绑定原提案；SI2 和
SI3 只消费 Decision，不消费 Proposal。当前本地 CLI 只能记录确认身份，
不能完成真实身份认证，正式 API/CI 需要在调用控制器前认证 Reviewer。

门禁规则：

- 所有 SOURCE_CODE 路由都必须提供源码复现、Context 消费后失败或结构性源码缺陷证据；
- 如果 Finding 偏业务语义或根因仍不明确，还必须证明 Context 规则或生成 SQL 已经正确，或者经过复核的源码契约明确拥有该行为；
- 外层 Eval 只判断候选是否通过冻结标准，不能替代“修复层级是否正确”的判断。

## 八、当前真实完成度

- SI0：已实现
- SI1：已实现
- SI2：已实现并真实运行
- 外层 Eval：已实现
- 自动根因诊断：未实现
- SI3：development-only 控制器和真实最小案例已实现
- SI3 Docker/CI 正式执行：未实现
- 自动审批/发布：明确不实现

这次 CNY 案例中，系统真实完成了 SI2 和外层评测；发现总结接口问题后，是我们人工检查源码并修改的，并不是系统自动转交 SI3。

因此，现在最准确、不过度设计的架构是：

```text
Evidence
  → EvalTarget
  → RoutingProposal（Codex/调用方提出建议并附证据）
  → 确定性证据门禁
  → 人工确认后的 RoutingDecision（选择 Context 或 Code）
  → Codex 生成候选
  → 确定性 Eval
  → 人工 Review
```

“自动根因诊断”和“SI2 自动转 SI3”都不是 MVP 必需能力，可以以后按真实失败数量再决定是否实现。

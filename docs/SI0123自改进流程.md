# 可以用这次“已实现收入”案例理解整个自改进流程

## 真实问题

用户问：

> What is the total realized revenue?

旧运行结果是：

答案：$1,131.70
SQL 条件：status != 'cancelled'

但业务人员明确纠正：

只有 completed 订单算已实现收入
金额单位是 CNY
正确结果是 721.80 CNY

## 自改进流程

错误 Trace + 业务纠正
→ SI0 FailureCase
→ SI1 GroupedFinding
→ 冻结 EvalTarget
→ SI2 Codex 修改 Wren 候选
→ 外层真实评测
→ REVIEW_REQUIRED

### 1. SI0 保存错误事实

系统保存旧 SQL、错误答案和自然语言业务纠正，但不立即修改任何内容。

### 2. SI1 冻结验收标准

在 Codex 开始工作前，外层系统固定以下要求：

结果：721.80，容差 0.001
SQL：必须包含 status = 'completed'
答案：必须包含 CNY
答案：禁止包含 $
重复验证：3 次

Codex 无权修改这些标准。

### 3. SI2 真实调用 Codex

真实调用了宿主 Codex CLI 的 gpt-5.6-sol。Codex 只能修改复制出来的 Wren candidate，不能修改源码、Git、Registry 或评测标准。

它最终保留了正确 SQL：

```sql
SELECT SUM(total_amount) AS realized_revenue
FROM orders
WHERE status = 'completed'
```

并将对应 NL-SQL 示例调整为用户真实问题。

### 4. 外层评测发现新问题

StarRocks 查询返回了正确数值 721.80，SQL 也正确，但 DeepSeek 总结成：

$721.80

这说明 Wren Context 已经改对，但运行时总结阶段没有收到 Context 中的 CNY 信息。

这个问题不应继续让 SI2 修改 Context，因为根因在项目源码，理论上应转交未来的 SI3。由于 SI3 尚未实现，这次由我们手动修复总结接口，让它消费 Wren Context。

### 5. 再次评测

没有再次调用 Codex，只复用了原 candidate：

Smoke：3/3
冻结目标：3/3
答案：721.80 CNY
状态：REVIEW_REQUIRED

## 安全结果

- Codex 确实参与了真实 Context 改进。
- Codex 没有修改项目源码。
- Codex 没有修改 EvalTarget。
- 候选没有自动审批或发布。
- 开发态候选被标记为 release_eligible=false。
- Improvement Job 仍为 PREPARED，没有正式 receipt 或 JobResult。

这个案例体现的并不是“Codex 随意重写自己”，而是：

> 生产错误和业务纠正驱动受控候选修改；外层系统掌握评测、权限和发布权，并把 Context 问题与源码问题路由到不同改进阶段。
